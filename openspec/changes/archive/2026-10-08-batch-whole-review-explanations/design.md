# Design

## Context

See proposal.md for motivation. Today `diff.lua` builds and double-checks a complete comparison, but its collection limits and final `prompt.build` call require that snapshot to fit one prompt. `prompt.context` removes manifest copies of source lines but still includes old/new versions plus unified patches. `session.launch` owns one invocation, validates a version-2 response, then distributes file notes and installs the narrative. `model.lua` already validates exact paths, independent old/new coordinates, chunk coverage, and file-contained anchors. The CLI decoders in `agent.lua` select successfully completed text without knowing the explanation schema.

`remove-structural-explanations` and `unify-explanation-commands` are implemented. The public dispatcher is `Explainr [file|selection|hunk|review]` / `explain(scope, selection)`: file routing follows source-window ownership, selection remains code, and hunk requires a coherent Diffview source. Associated readers resolve their followed source. `Explainr review` outside Diffview already opens an owned HEAD-to-working-tree comparison through `diffview.open_review()`, then hands invocation-time configuration and a coherent source to the ordinary session pipeline. `ExplainrReview` only displays a narrative. Preserve these contracts rather than reintroduce separate commands or routing inside the cache.

The current specs explicitly require one invocation, reject splitting, require version 2 on the review wire, forbid progress before the whole response validates, and prohibit disk result history. This change deliberately replaces those constraints, not the exact-comparison or atomic-display guarantees. File/hunk auto/focused behavior stays unchanged. Current code fingerprints include buffer IDs inside selection spans; session cache keys include decoder-function identity. Neither is directly suitable for cross-process reuse.

## Goals / Non-Goals

**Goals:** Bound each inference operation independently of the local snapshot; account for all eligible source text across a review; retain exact evidence provenance across synthesis; isolate failed work without exposing an incomplete review; preserve navigation, queue, cancellation, and freshness ownership.

**Non-Goals:** See proposal.md. In particular, no model-directed source fetching, provider-specific tokenizer or token-limit enforcement, automatic repair loops, or promise that any size of comparison can be explained. Host coverage accounting proves what was supplied and validated, not that a model understood every line or found every relationship.

## Decisions

### 1. One frozen comparison, separate bounded request views

Comparison opening remains cancellable preflight, not part of annotation or a separate cache/agent path. For an outside review, capture current coherent contents only after readiness, using the configuration captured at invocation, including the new review/cache options. Preserve opening deduplication, cancellation, the independent opening deadline, focus behavior, and Auto suppression through handoff to one review job. Failed, cancelled or replaced opening callbacks must not start collection, restore a cached answer, or dispatch inference.

The opened HEAD-to-working-tree pair represents net staged-plus-unstaged changes; an unstaged undo can cancel a staged edit. Existing views retain their exact revisions, staged/working set and filters. Preserve source-repository/linked-worktree resolution and unnamed-source cwd fallback. Follow Diffview's effective untracked policy (the tested version excludes genuinely untracked files from HEAD comparisons, but includes staged additions); overlay unsaved buffers only for manifest entries. Do not save, stage, invent unsaved-only entries, or broaden the comparison while partitioning it.

Keep capture, revision resolution, unsaved-buffer overlays, and double-read race checks in `diff.lua`. For explicit review only, decouple full snapshot admission from `context.max_bytes`; use a separate local snapshot cap. Keep source text once per version in the retained review job and reference it from units instead of deep-copying the entire snapshot into every checkpoint. Preserve the complete manifest, old/new identities, filters, hunks, binary/empty metadata, and content guards.

`prompt.lua` serializes request-specific views. Review requests include source chunks with original `start_line`, independent old/new coordinates, exact paths, and hunk indices. They omit unified patch strings when those lines are already supplied. The complete snapshot remains the source of truth, but only the unit's supplied ranges authorize citations. Do not validate a unit against the full local snapshot and thereby permit citations the model never received.

Alternative: send a file attachment or resume one agent conversation. Neither inherently reduces model context, and continuation risks compaction and mutable external history. Independent stdin requests retain the existing transport and permission boundary.

### 2. Deterministic annotation units and honest coverage

Add a cohesive `review.lua` planner/job module; leave Diffview inspection/opening in `diffview.lua`, session/display ownership in `session.lua`, serialization in `prompt.lua`, and output validation in `model.lua`. A unit identifies one file or one fragment of its available versions. Deterministically pack affordable units into requests using exact serialized input sizes and conservative output allocations. Prioritize changed decision documents, then group by directory/path; this is reproducible locality, not a claim of dependency analysis.

Prefer whole-file units. When a file cannot fit, partition both complete textual versions into disjoint owned line intervals, retaining optional overlapping surroundings as evidence only. Prefer hunk boundaries and keep paired old/new changes together when affordable. A large hunk can span units with explicit fragment markers; never renumber or silently discard its remaining lines. Pairing across an unavailable interval is not permitted. Added/deleted and empty sides retain their existing meanings. A single line plus mandatory overhead that cannot fit is an explicit planning failure, not byte truncation.

Before inference, verify that the union of owned intervals is exactly every available old/new text range for every eligible file, with neither holes nor duplicate ownership. Each changed span and every unchanged paragraph in a changed decision document is therefore supplied in some annotation unit. Optional overlap does not count twice. Requests declare local coverage rather than claiming the whole comparison is visible to that invocation.

Units with complete file versions request the existing optional file overview. Fragment units do not request or accept a fabricated whole-file overview; they return range notes. A split file may consequently have no overview, which remains optional. Aggregate validated fragment notes in stable source/unit order, suppressing only exact duplicates; never join ranges or rewrite prose heuristically. Empty notes explicitly acknowledge a unit, rather than implying missing coverage.

Alternative: only send changed hunks. It is smaller, but silently drops unchanged requirements and context that the current review contract supplies. This design preserves complete text coverage across calls, not simultaneous full-context reasoning.

### 3. Explicit input, output, snapshot, and call limits

Introduce `review` configuration, captured with the job:

| Setting | Proposed default | Meaning |
| --- | --- | --- |
| `request_max_bytes` | 65536 | Complete UTF-8 prompt cap; effective cap is the minimum of this and `context.max_bytes`. |
| `response_max_bytes` | 32768 | Maximum decoded final JSON text per review invocation, including findings. |
| `max_snapshot_bytes` | 16777216 | Maximum canonical serialized review data retained from collection, excluding duplicate display/capture structures. |
| `max_requests` | 128 | Maximum new external invocations during one explicit run/resume, across annotation, reduction, and synthesis. |

All values are positive finite integers. These defaults are conservative starting points, not provider-capacity guarantees. Raising `context.max_bytes` alone does not enlarge review batches. Existing `ai.timeout_ms` applies to each invocation; no hidden global timeout replaces it. The snapshot cap is an admission bound, not an exact Lua heap-usage claim.

Budget instructions, schemas, IDs, evidence packets, and metadata, not just code bytes. Reserve output by allocating at least 8192 decoded bytes per annotation unit when packing; a smaller configured response cap allows one unit with that smaller allowance, never a zero-unit batch. Include finite note/finding/detail allowances in prompts and validate their declared limits and total decoded bytes. At most eight notes and four findings per unit are requested, further reduced to fit the allocation. Sparse notes are legitimate; dropping required unit acknowledgements is not. Output allocations reduce risk, but cannot force a CLI's model output limit or guarantee compliance. Oversized/truncated output fails that invocation without repair or automatic subdivision.

Preflight all annotation requests before launching any. Synthesis depends on actual findings, so its later admission failures retain annotation checkpoints. Count launches before dispatch; never exceed `max_requests`, including failures. A further explicit resume grants a new bounded run, not an automatic retry. Bound in-memory checkpoint retention to the latest unfinished job per tab/comparison owner; replacing it evicts its uninstalled results.

### 4. Version-3 phase contracts and source-grounded synthesis

Use version 3 for review wire responses, with explicit `phase`, `request_id`, and `snapshot_id`. Annotation responses acknowledge exactly the host-assigned unit IDs and return notes plus compact findings. Findings contain concise text, intent basis, file references, and source citations; distinguish them from final file-note details. Code/file/hunk remains version 1. Generic final-text decoders are unchanged; a version-2-only review wrapper fails clearly rather than being silently adapted or retried.

After annotation, synthesis receives compact findings, relevant manifest metadata, and exact original source excerpts for their citations, extracted by the host from the frozen snapshot. Optional decision-document evidence can similarly accompany annotation units when affordable, with supplied coverage recorded. Derived findings are explicitly untrusted interpretations, not proof. Documented intent requires actual source evidence in the current request. Findings without supporting source remain inferred/unknown and cannot be promoted to documented just because another model asserted them.

If all synthesis input fits, request the final narrative. Otherwise deterministically pack bounded reduction requests that combine findings into smaller cited findings, then repeat until the final narrative input fits. Each reduction acknowledges exactly its assigned child result IDs. The host retains transitive coverage, independently of which findings the model highlights. Rehydrate original source citations at every level; validate cited ranges against that level's transmitted excerpts. A reducer cannot cite an unseen range even if an earlier unit saw it. Final synthesis receives the complete compact manifest plus its bounded findings/evidence packet so binary/empty entries remain available as references.

Reduction must strictly reduce the serialized findings-plus-rehydrated-evidence input needed for the next level; otherwise fail explicitly. An indivisible finding/evidence packet or final manifest that cannot fit also fails. Do not silently clip citations, lose a child from the coverage ledger, recurse indefinitely, or send one oversized final request. The shared invocation cap bounds all levels. Reduction can select salient findings; it must not claim to preserve every semantic interaction. Narrative prompts disclose that reasoning was distributed and request caveats where source context is insufficient.

The final synthesis returns only the narrative, never all file notes again. The host assembles the familiar version-2 internal result (`review` plus exactly one `files` entry per eligible file) from validated units and the narrative, retaining unit provenance. Reuse existing UI/retention shapes and final structural checks, but do not discard the stricter per-invocation evidence checks after aggregation.

Alternative: concatenate file overviews into a narrative. That avoids a call but does not explain relationships. Alternative: unbounded model-directed follow-ups. That introduces a tool protocol and less predictable cost; defer it to snapshot-only retrieval work.

### 5. Comparison-owned execution with internal checkpoints

One explicit review occupies one FIFO request slot until success, cancellation, or failure. Its units run sequentially through the existing configured command. Keep navigation automation suppressed throughout the job and between phases; explicit later file/hunk requests remain queued. A failure stops the review job and advances the existing explicit queue, without launching repair, provider fallback, or automatic file work.

Checkpoint a unit only after successful process exit, phase/schema/range validation, response-budget validation, and current snapshot/generation checks. Key reuse by whole snapshot fingerprint, protocol/planner version, exact unit request/coverage, and captured AI/context/review settings, including custom decoder identity. Conservative whole-snapshot invalidation prevents notes from surviving changed decision evidence. Navigation does not invalidate work; discarded unsaved content does.

Repeating `Explainr review` or `require("explainr").explain("review")` in the owning comparison (including its file panel or associated reader) recollects/revalidates and resumes a matching unfinished job, skipping validated annotation/reduction/synthesis results. It retries the failed invocation and then remaining work, not only the individual invalid item inside that invocation. A fully completed exact match reuses the assembled answer without inference. `ExplainrRefresh` in Review discards checkpoints and regenerates all phases; File refresh remains file/hunk-scoped. No new retry command is necessary.

Repeating review during opening coalesces with that pending operation; it is not checkpoint resume. After handoff, invoking review from ordinary code opens a new comparison under the existing command contract and does not adopt another tab's unfinished checkpoints, even for identical contents. Completed semantic cache entries may be reused across equivalent views; unfinished jobs remain owner-local. Resume diagnostics must direct the user to the owning comparison or its reader.

Cancel stops the active process and scheduling, clears queued requests under existing rules, and keeps already validated internal checkpoints eligible for an explicit resume while the comparison owner remains open. Close, comparison replacement, and stale snapshot eviction discard unfinished-job checkpoints. Late callbacks after any cancellation cannot add checkpoints or install output. Only completed validated explanations, not unfinished jobs, persist across Neovim restarts through the shared cache below.

Only after all required units and the final narrative validate does one final freshness check allow atomic installation. Until then, retain older fresh visible explanations; new checkpoints are not exposed as completed file answers or used to satisfy independent file requests. Reading completed details never invokes AI.

### 6. Measured status, unchanged reading surfaces

Use the existing header/status projection: collecting/planning, `Annotations 3/12`, reducing findings, synthesizing narrative, and Ready. Annotation totals refer to planned units, not model tokens, files, percent, or ETA. Only validated checkpoints advance the count; resumed checkpoints count immediately after revalidation. Synthesis is a separate phase, so annotations 12/12 does not mean the review is complete.

Before handoff, retain the existing opening notification without creating a reader against unready buffers or inventing annotation counts. A completed cache hit after readiness/capture transitions to cached-ready without fabricating annotation or synthesis work. Opening failures identify preflight, not a failed annotation unit.

Failures identify phase/unit, completed-unit count, relevant byte/call limit when applicable, and `:Explainr review` in the owning comparison or reader as explicit resume versus Refresh as regeneration. Do not dump code, full prompts, or credentials into diagnostics. Narrow headers keep mode/state/Auto priorities. Status transitions preserve focus, current file, expanded detail, and narrative scroll; existing Review loading decorations span the whole pending job.

### 7. One persistent completed-result cache for all five scopes

Add `cache.lua` as a common completed-result store used around session request validation, not inside the review executor or CLI decoder. It supports visual selection, code file, diff file, diff hunk, and whole review. Do not persist intermediate annotation/reduction responses as standalone answers. A complete review entry retains its assembled result and per-invocation provenance, but no executable job state. Function/class removal is already implemented; scope validation precedes cache lookup, so retired scopes cannot be revived by disk entries.

Use a versioned, canonical SHA-256 request identity with these parts:

- Source namespace: canonical repository/worktree root where applicable; otherwise canonical cwd plus named-file path. Different checkouts remain isolated initially, even with equal patches. Do not key by remote URL alone.
- Resolved semantic mode, scope, exact normalized target, and every supplied contextual file/range's content hash. Include independent old/new paths, modes, absent/empty/binary state, EOF semantics, resolved revision pair, staged/working kind, filters, untracked policy, and effective coverage. Same patch with different surrounding code or decision evidence is a miss. Unified file scope does not merge code-file and diff-file identities even when their windows share a buffer; selection remains code regardless of its originating window.
- Code selections: selected text plus ordered per-line byte spans and virtual offsets, normalized selection semantics, without embedded buffer IDs or endpoint direction artifacts. Hash the whole supplied code buffer, not only the selection. Named paths stay source-specific. For unnamed buffers, serialize a stable logical source label in prompts/cache records and bind only structured source references to the current buffer during installation; never persist `[buffer:N]` or rewrite arbitrary Markdown prose. Runtime window/tick checks remain separate.
- Generation identity: explicit cache-format, prompt/response-contract and planner versions; command argv digest, built-in decoder name or explicit custom-decoder key; output-affecting context/planning settings; user cache namespace. Exclude cursor, selected Diffview file for review, window/tab/buffer IDs, filesystem timestamps, timeout, cache size, and operational call/snapshot caps. Input budgets that alter actual coverage or batch planning remain identity inputs. Same-process function identity checks still apply for custom decoders.

Public command versus Lua invocation and manual versus automatic Diffview opening are not generation identity. After fresh capture, equivalent resolved comparisons with the same namespace, inputs and generation settings share completed answers, including across restarts. Do not omit resolved mode or comparison metadata merely because both requests use `Explainr file` or `Explainr review`.

Use `cache = { enabled = true, max_bytes = 104857600, namespace = "default", decoder_key = nil }`. `max_bytes` is a positive finite integer; namespace and an explicitly supplied decoder_key are nonempty strings. A custom decoder without a stable decoder_key opts out of disk reads/writes while retaining existing in-memory behavior. Explainr cannot discover changes hidden behind external agent config, environment or wrapper scripts: users must change namespace/decoder_key or Refresh when that hidden contract changes. Hash command configuration for identity without storing raw argv or credentials in cache payloads.

Lookup after fresh source capture and target/coverage resolution, before dispatch. A complete-review hit needs the current full snapshot and generation identity, but no model calls or replay of reduction. Revalidate the envelope, supported scope/version, exact request identity, note/narrative schemas, complete review coverage, and stored per-result supplied-range provenance against the recaptured snapshot, then perform the normal last freshness/ownership check and bind current display state. Cancellation during disk I/O cannot install a late hit. A full-file result is not substituted for a selection, nor a review-generated file result for an independently requested focused file unless target, generation and effective provenance actually match; do not invent cross-scope aliases.

Alternative: hash the raw prompt. That includes ephemeral buffer descriptors today and cannot represent a completed multi-invocation review before generation. A canonical semantic request record gives a stable key while retaining exact dependency and protocol checks. Reuse the stable serialization approach already in `diff.lua`, not `vim.inspect` or unordered JSON objects as a disk identity contract.

### 8. Private disposable JSON storage with explicit controls

Store one completed record at `stdpath("cache")/explainr/results/v1/<source-hash>/<request-key>.json`. Each contains identity/version digests, normalized target/coverage metadata, validated result, provenance references/ranges, and creation/access timestamps. Do not store full source, prompts, process streams, credentials, closures, buffer/window objects, or unfinished checkpoint state. Result prose can contain sensitive source snippets: this is private plaintext, not encryption. Use 0700 directories and 0600 files on supported systems. Reject symlink/nonregular owned entry paths and never follow cache content as executable code or arbitrary filesystem paths.

Read asynchronously with a size bound before JSON decoding. Write a unique temporary file in the same owned directory, then atomically rename a complete record. Concurrent Neovim writers can duplicate inference on simultaneous misses; only valid complete entries can win replacement. Cross-process single-flight inference is out of scope. Serialize mutation/pruning/clear operations with a short-lived filesystem lock, with bounded waiting and conservative stale-owner recovery; contention skips the cache operation rather than blocking explanation generation. Enforce the 100 MiB default total for committed records, prune least-recently-used entries under that lock, and skip entries individually larger than the limit. Temporary writes remain bounded and cleaned up. No TTL is required: content/contract identity determines validity; eviction or external cleanup naturally creates a miss.

`cache.enabled=false` disables persistent reads/writes, not current-session accepted-note retention. Add `:ExplainrCacheClear` and `require("explainr").clear_cache()` to clear completed disk entries and reusable in-memory answers in the current process without closing panes or discarding displayed valid notes. It targets only the plugin's owned results root, never repository files or unrelated Neovim caches. In-flight generation in this process uses a cache generation token so a pre-clear job cannot immediately repopulate disk; another running Neovim can create later entries, which must be documented. Unfinished review checkpoints remain governed by Cancel/Refresh, not cache clear.

Refresh bypasses both completed-result caches for its current scope; Review Refresh also bypasses unfinished checkpoints. Do not delete the previous disk entry until successful validated replacement is ready. Cache read/parse/version/identity failures are misses; write/prune/permission failures produce a bounded warning and do not turn a valid explanation into a failed request. Reuse continues through the existing `Ready · cached` state, without fabricating generation progress. Documentation must describe persistent local sensitive text, opt-out/clear, eviction, and hidden external configuration invalidation.

Alternative: SQLite. Direct content-addressed lookup and bounded directory pruning do not warrant a database dependency. The short lock protects file-store maintenance, not a new persistent job service.

## Risks / Trade-offs

- More calls and repeated evidence increase latency and possibly cost → sequential scheduling, bounded runs, explicit review-only generation, checkpoints, and clear documentation; no billing-savings promise.
- Distributed context can miss relationships a single large model call would notice → supporting evidence packets and dedicated synthesis with original citations; acknowledge semantic limits rather than equating coverage with correctness.
- Reduction can overgeneralize or retain too much evidence → validate provenance at every level, require progress in serialized size, and fail rather than erase required grounding.
- Small response allowances can reduce explanation usefulness → keep full detail in accepted notes, test nontrivial asymmetric examples, expose finite settings, and never confuse sparse notes with exhaustive analysis.
- Larger local snapshots increase memory and recollection cost → separate snapshot cap, shared immutable data, bounded checkpoint retention, cancellable yielded collection, and no claim that native diff/encoding is off-thread.
- CLI compaction and provider limits remain outside host control → smaller independent calls reduce exposure but do not guarantee avoidance; report errors without editing user OpenCode settings or weakening anchor validation.
- Persistent output can contain private code → private permissions, no raw source/prompt persistence, explicit opt-out/clear, bounded retention, and no claim of encryption or portability across users/machines.
- Session-specific selection fields or overly broad cache keys can cause wrong hits → normalize only transient identities, preserve exact columns/context, reject unsupported scopes before lookup, and verify reuse using separate Neovim processes with deliberately different buffer numbering.

## Migration Plan

Implement and verify snapshot/request separation first without changing file/hunk behavior. Add pure deterministic planning and phase validation, then job execution/checkpoints, atomic assembly, status projection, and the shared completed-result cache. Build on the already-applied `remove-structural-explanations` and `unify-explanation-commands` changes; neither must be archived first. Preserve their routing, opening and display-only contracts. When syncing overlapping requirements such as Hunk and file explanation focus and Whole-comparison explanation scope, merge unified command/API wording and source restrictions with this change's bounded job/coverage semantics; never restore old aliases, structural scopes or single-invocation constraints. Update help and custom-wrapper examples for version 3, multi-call cost, byte limits, caching privacy, owner-local resume versus refresh, and scope limitations. Main specs receive these deltas only through normal sync/archive, not during this artifact update.

Use offline fake agents for annotation/reduction/synthesis, adversarial incomplete outputs, and delayed/cancelled processes. Extend the disposable Diffview fixture with unequal old/new lengths, a split large hunk, a changed document with unchanged rationale, and cross-file evidence. Extend `tests/commands_test.lua` to verify opening-to-job handoff, captured configuration, cancellation, duplicate events and net working-tree semantics with batching enabled. Run targeted suites and the complete headless suite. Render and inspect existing File/Review, opening-to-job/cache-hit transitions, intermediate progress, synthesis, failure/resume, cancellation, narrow-header, and navigation states using the existing visual workflow; no paid inference is required for acceptance.

Add cross-process cache acceptance tests using an isolated temporary XDG cache root, never the user's real cache. Exercise all five scopes, code/diff file separation for shared buffers, equivalent manually/automatically opened review reuse, unnamed/multibyte/block selections, context-only misses, corrupt/truncated/oversized entries, concurrent writers/clear, cancellation during lookup, failed Refresh preservation, and zero fake-agent calls on a validated hit. Keep UI captures for cached restoration as well as generation states.

Rollback restores the previous explicit review protocol and clears process-local unfinished jobs by restarting Neovim. Older code ignores the new versioned cache directory; clearing it is safe because it contains only disposable completed results. No external configuration, repository content, or database migration is involved.
