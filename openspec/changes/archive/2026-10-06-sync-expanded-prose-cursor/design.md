# Design

## Context

See `proposal.md` for motivation and `specs/aligned-explanation-ui/spec.md` for the behavior contract. Design is warranted because cursor mapping, native scrolling and anchor boundaries need an explicit ordering before implementation.

`lua/explainr/ui.lua` owns both modes. `pane:detail()` records source-backed leading/trailing rows in `detail_layout.rows`, but only marks Markdown rows active. `pane:sync()` resolves source-backed rows through comparison coordinates; prose falls through to `pane:scroll()`. With no viewport delta, that path never moves the source cursor. The investigation reproduced a 37–58 diff anchor remaining at line 37 while moving through paragraphs; a separate 4–25 code-mode check confirmed continuation rows still synchronize.

`M.project(win)` describes the current source viewport in display rows, including wraps, folds, filler and empty EOF space. `pane:ranges()`, `pane:coordinates()`, `pane:locate()` and `pane:sync_sources()` already own comparison geometry. The existing expanded-viewport test exercises a 600-line explanation over a one-line anchor and must retain free scrolling, including when that anchor is off-screen.

## Goals / Non-Goals

**Goals:**
- Add visual-row cursor selection inside the existing expanded synchronization path, with no new navigation controller or key remaps.
- Keep display positions and anchor eligibility separate: prose height controls reading layout, not the extent of code ownership.
- Preserve source viewports, explanation focus and native source-driven behavior while updating the appropriate source line.

**Non-Goals:**
- Infer which paragraph semantically explains which code line, or distribute paragraphs proportionally across an anchor.
- Redesign detail layout, focus surfaces, Markdown rendering or collapsed navigation.
- Require a renderer, change source text/options, or force every source cursor column onto the exact wrapped segment. This change synchronizes source lines; wrapped source segments still represent the same line.

## Decisions

### 1. Extend the prose branch of `pane:sync()`

Retain the existing mapped-context branch, including collapse at an outside destination. For explanation-driven motion in the Markdown span, synchronize pending viewport movement first, then resolve the prose cursor's relative content-screen row against a fresh source viewport projection. Source-driven calls keep their existing scrolling path and do not apply the inactive prose cursor's position to code.

Do not perform prose mapping as part of opening detail or explicit n/p entry selection. Those operations must continue to preserve expansion geometry and select the requested entry. Any deferred cursor event generated by initialization must not be mistaken for a user motion.

**Alternatives rejected:** mapping Markdown row numbers fails when prose wraps or context is trimmed; counting j/k actions misses searches, screen motions and horizontal motion across wraps; adding prose mapping to every `pane:scroll()` call would override source-driven navigation and expansion.

### 2. Use the actual cursor display position and current source geometry

Measure the explanation cursor's display row at its actual column, relative to its content area, excluding the winbar. Do not measure only the first column of the paragraph: later wrapped segments have the same buffer line but a different screen row. Resolve that relative row in `M.project(layout.source)` after paired scrolling, rather than reusing the projection captured when expansion opened.

Reuse comparison-coordinate and folded-target resolution from mapped context. Where the followed side has diff filler, select the side owning a real line at that coordinate, then synchronize its counterpart through `pane:sync_sources()`. Resolve a closed fold to its start without opening it. Prefer the followed side when both sides have a real eligible target.

**Alternative rejected:** aligning raw terminal row numbers across windows ignores different header offsets; using the opening projection becomes stale after scrolling.

### 3. Bound selection to visible anchors, not the whole card

Retain the expanded entries' normalized anchor ranges with detail layout metadata, including all entries in a combined folded card, rather than inventing a second anchor model. Treat a folded display stop intersecting an anchor as eligible. Preserve separate anchor intervals; do not fill unanchored gaps between them.

Select the eligible source display stop at the cursor's relative row. If that row is outside the eligible set, choose the nearest visible eligible stop, with ties choosing the earlier display row. This clamps above/below the visible range, handles disjoint ranges and excludes empty EOF rows. If no real anchored target is visible in paired sources, leave the source cursor as native scrolling positioned it.

This visible-only rule is deliberate: selecting an off-screen boundary could reverse paired scrolling or make the cursor invisible. Native scroll commands may move source cursors outside anchors to keep them visible; the new prose-selection step does not manufacture an unrelated target or force an off-screen anchor back into view.

**Alternatives rejected:** clamping to an off-screen absolute anchor fights long-detail scrolling; mapping the whole tinted card to code can select unrelated lines; freezing at the previous cursor position when anchors are visible recreates the reported mismatch.

### 4. Preserve synchronization lifecycle and viewport ownership

Apply source cursor updates under the existing synchronization guard, without taking focus or mutating source options. Keep the source's current column where possible, clamped to the target line length; fold starts and filler resolution remain native navigation stops. Preserve the post-scroll view while selecting an eligible line, accounting for scrolloff and native limits. Update `scroll_views` after the final cursor/view changes so later CursorMoved, WinScrolled and SafeState callbacks do not replay a stale movement.

The new mapping must be idempotent across repeated events and must not route back through overview alignment. Collapse, stale-data cleanup, and n/p navigation continue to use their existing ownership paths.

## Risks / Trade-offs

- Cursor position APIs can report the start of a wrapped paragraph or stale screen geometry → test later segments of one paragraph using actual cursor columns and executed editor motions, with and without optional Markdown rendering when available.
- Setting a source cursor can trigger scrolloff or paired diff scrolling → assert unchanged post-scroll source views and explanation focus, and refresh cached views only after the guarded update.
- A fresh viewport scan on each prose cursor event adds work → reuse existing comparison caches and bound projection/selection to visible rows; do not rebuild the whole overview.
- Visual-row correspondence is not a semantic paragraph-to-code relationship → document it as positional synchronization and keep anchor bounds authoritative.
- A folded stop can start before the literal anchor, and a paired diff side can lack a matching real line → keep the existing fold-start/native counterpart behavior rather than unfolding code or inventing filler cursors.

## Migration Plan

No data or configuration migration is required. Update `README.md` and `doc/explainr.txt` when implementation lands; the help text currently says ordinary detail movement is independent of code. The delta deliberately revises the long-paragraph scenario without removing the prohibition on Markdown-line-number mapping. Rollback consists of reverting the prose synchronization implementation, its behavior-specific tests and documentation.
